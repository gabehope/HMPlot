# Agent-task evaluation

This local harness measures whether coding agents can make a working chart with HMPlot or another plotting library. It contains **63 tasks**: 22 seeded tasks written around HMPlot's strengths (`hmplot`), 32 seeded ordinary charts where HMPlot may lose (`general`: bars, distributions, annotation, layouts, waterfalls, calendars and more), three real-data tasks, and six curated MatPlotBench tasks. Every task has a category (basic, statistical, layout and annotation, interaction, scale, animation and simulation, maps and 3D, export), and the report gives totals per category. The Python and JavaScript tracks share task wording where a task supports both. Generated data, downloaded bytes, agent traces, screenshots, venvs, and reports stay in a scratch root outside the repository. The harness does not publish results.

## Hard prompts: models and pipeline docs

`complex.pipelines.toml` runs the original ten complex prompts and five D3-inspired prompts
with `gpt-6-luna` and `gpt-6.1-sol`, each under `hmplot-standard`, `hmplot-fluent` and `free`:
**90 trials**, one repetition, **two corrections** (at most **270 implementation sessions**).
Both HMPlot conditions use one wheel and the two doc sets generated by `npm run build:llm-docs`;
the standard condition uses the generated standard set rather than a possibly stale site build.
No judge is configured: generation does not restart model review.

The five additional tasks live in `tasks/d3-hard`, so the original `complex` source remains ten
prompts: brushable parallel coordinates, a zoomable portfolio treemap, a streamgraph with a
linked date lens, hierarchical community edge bundling, and linked regional anomaly calendars.
Their `inspiration` metadata links the original D3/Observable examples. These are new prompts
with seeded local data, not copied notebook code or external-data fetch requirements. The
existing cars, contacts and sensor datasets are reused; portfolio and source-traffic data have
new deterministic generators. All conditions get identical prompts and bytes.

Browser text/view checks establish that a chart rendered; generic interaction differences do
not establish correct membership, totals, hierarchy navigation, bundling or calendar placement.
Those remain `unknown` until reviewed. Do not count a changing or disappearing picture as a
passing interaction. Keep the final program, all correction attempts and screenshots for review.
HMPlot conditions additionally require a live HMPlot canvas/runtime in the submitted HTML and
nonempty HMPlot marks in the inspected program. An unused empty Plot alongside custom SVG is
rejected; the shared preamble states this explicitly. These checks establish library use, not
that all task requirements are satisfied; semantic and visual review is still needed.

## Click drilldown acceptance

The `click-drilldown` task has an explicit `interaction/click` check. The HMPlot adapter in
[click_drilldown.py](agenteval/click_drilldown.py) independently sums the supplied CSV's 2024
rows, then compares exported rectangular bar geometry against every region and product total.
At DPR 2 with HTTP(S) blocked it checks initial totals, North, South, repeated South, then an
active North selection cleared by the background. Each step saves `click-<step>.png` and records
expected totals and measured geometry in `metrics.click_drilldown`; live canvas pixels must
also paint every bar interior. The tolerance is 0.75 CSS pixels for fractional viewport rounding.
This deliberately supports vertical, linear HMPlot bars; other library adapters report unknown,
and an unsupported geometry or wrong sum fails. Screenshot differences cannot pass this check.
The reference is [references/click-drilldown/hmplot.py](references/click-drilldown/hmplot.py).
Run `PYTHONPATH=eval/agent-tasks .venv/bin/python -m unittest discover -s eval/agent-tasks -p test_click_drilldown.py`
for the CSV/geometry regressions. Re-run a reference through the harness to exercise real clicks.

## The default comparison: HMPlot against free choice

The question the default config answers is whether an agent does better with HMPlot than on its own (TODO Stage 131). [benchmark.example.toml](benchmark.example.toml) runs every task in two conditions, paired: `hmplot` (local docs and the skill) and `free` (the usual Python libraries installed, no HMPlot, and the agent may also write the chart by hand); the JavaScript track pairs `hmplot-js` with `free-js` (D3, Observable Plot or deck.gl, or none). `hmplot-cold` (no docs, no skill) runs on a ten-task sample, set by `[library_tasks]`, to track what models know of HMPlot without help. The per-library conditions (Plotly, Altair and the rest) stay available to a config; they are no longer the default, because they spend the budget on comparisons with each library rather than on more prompts. ## The data-pipeline comparison: nested blocks against chains

[pipelines.toml](pipelines.toml) asks whether agents write HMPlot's live data pipelines better when the docs teach them as chains, as polars does (`hm.Data(df).filter(...).group_by("region").agg(total=hm.col.revenue.sum())`, TODO Stage 144), than as nested `with hm.Filter(...):` blocks. Its two conditions run the same package with the same preamble and differ only in their docs and skill: `hmplot-standard` reads `build-llm/standard` and `skills/hmplot`; `hmplot-fluent` reads `build-llm/fluent` and `variants/fluent/skill`. Both doc sets come from one script, `npm run build:llm-docs` (scripts/build-llm-docs.mjs), so a page differs between them only where it shows a pipeline: the recipes (`src/recipes/fluent` replaces the seven that filter, group or join), the Data, Filter, Calculate, Group, Join and Sort reference pages (their Python example is a chain, from `src/recipes/fluent/reference`, and a line names the method), a "Data pipelines" section at the top of recipes.md and the skill, and, on the other pages that still nest transforms (the transforms guide, 15 reference pages, 31 gallery examples), a note under the title that a chain builds the same transforms. `node scripts/generate-patterns.mjs` writes the fluent skill from the standard one (fluentDocs.js lists each rewritten passage; it fails if the standard text changes under one). The tasks are the 17 whose reference solutions filter, group, calculate or join live data, two repetitions each; compare pass rate under review and tokens per success.

## Model first-pass review

Visual review of every render by hand does not scale to this many prompts. After a run, a model reviews each render first:

```sh
$PY eval/agent-tasks/benchmark.py model-review --config eval/agent-tasks/pilot.toml --root "$ROOT"
$PY eval/agent-tasks/benchmark.py accept-model-reviews --config eval/agent-tasks/pilot.toml --root "$ROOT"
```

- The reviewer is `[judge]`: a configured agent by ID (`agent = "codex"`), or its own `backend`, `binary` and `model`, so a reviewer model runs no trials. `--agent` overrides it.
- The review is blind. The reviewer gets a folder (in the run's audit directory) with the task's prompt and its renders (`screenshot.png`, `after.png` after the harness's interaction, `pdf.png`), never the program, the library or the condition, and writes `model-review.json` with a verdict, a reason and the problems it saw. Codex gets the images attached (`--image`); Claude and Gemini open the files. A run with no render fails without a model call; a reply without a valid verdict is recorded as an error, not a score.
- The browser checks stay authoritative where they decide. A model pass agrees with passing or undecided (`unknown`) checks; a model fail agrees only with failed checks. `accept-model-reviews` scores the runs where they agree (`review_source: model`), lists every disagreement for a human, and prints a seeded sample of accepted runs to spot-check. `benchmark.py review` (`review_source: human`) always wins and is never overwritten.
- The report shows the model's verdict, reason and problems beside each run, and `results.csv` carries `model_verdict`, `model_agrees_with_checks`, `review_source` and `category`.

The model review has been tested against fixture adapters only; its first live use is the pilot.

## Docs reading and the rest of a run

The report splits each run's tokens into what went to reading HMPlot's docs and skill and what went to the rest ([docs_usage.py](agenteval/docs_usage.py)), from the traces of the same runs. Exact from the trace: the commands that read `hmplot-docs/` or `hmplot-skill/`, the files they named, the characters they printed, and the steps before the first write of the solution. Estimated, and labeled so: the docs' tokens, each docs output counted at up to 10,000 tokens (four characters per token) when read and again for each later step that carries it, never more than the run reported. Codex's JSON reports one usage total per turn, not per request, so an exact split needs per-request usage (Claude's stream-json output, or Codex's session rollout). A trace with no tool steps (the Claude adapter's single JSON result) shows "not recorded", not zero. The totals table gives mean tokens per condition with the split.

## Task and run formats

Each `tasks/<source>/<id>.md` file has TOML metadata between `+++` lines and an effective Markdown prompt below it. The metadata includes `id`, `source`, `category`, `access` (`provided` or `agent_fetch`), `tracks`, `data` generator names, `[[sources]]` with exact HTTPS URL, destination, maximum bytes and SHA-256, and `[[checks]]`. For a MatPlotBench case it also has `upstream_id`. The prompt paragraph is identical across library conditions; [prompt.py](agenteval/prompt.py) adds a short library preamble and track-specific output instructions. `solution.py` is the Python deliverable; `solution.svelte` is the JavaScript deliverable. Both produce one self-contained `output/chart.html`; PDF tasks also produce `output/figure.pdf`.

A TOML [benchmark config](benchmark.example.toml) selects task IDs or whole sources, configured agent binaries and models, track-specific libraries, repetitions, and correction rounds. `[[task_overrides]]` is not used: per-task repetition overrides are `[task_overrides.<task-id>] repetitions = N`. `[library_tasks]` limits a condition to a sample of the selected tasks (`hmplot-cold = [...]`), and `[judge]` names the model reviewer. The example defaults to **one replication and one correction**. [smoke.codex.toml](smoke.codex.toml) selects one `scatter × hmplot × Codex` run with at most one correction. Run `benchmark.py plan` first to inspect the expanded matrix and maximum number of agent calls. A new agent adapter implements `Adapter.command`, `Adapter.parse`, and `Adapter.version` in [agents.py](agenteval/agents.py), then registers its backend in `ADAPTERS`.

```sh
ROOT="$(mktemp -d)"
CODEX_BIN=/path/to/codex
CLAUDE_BIN=/path/to/claude
GEMINI_BIN=/path/to/gemini
export CODEX_BIN CLAUDE_BIN GEMINI_BIN
npm run build:python
npm run build                         # local HMPlot docs used by guided conditions
npm run build:llm-docs                # the two doc sets of pipelines.toml (build-llm/)
python3 eval/agent-tasks/setup_env.py "$ROOT"
PY="$ROOT/venvs/harness/bin/python"
$PY eval/agent-tasks/benchmark.py plan --config eval/agent-tasks/benchmark.example.toml
$PY eval/agent-tasks/benchmark.py prepare-data --config eval/agent-tasks/benchmark.example.toml --root "$ROOT"
$PY eval/agent-tasks/benchmark.py probe --config eval/agent-tasks/benchmark.example.toml --root "$ROOT" --agent codex
# Inspect $ROOT/probes/codex-audit/session-0.stdout.jsonl, then record the review:
$PY eval/agent-tasks/benchmark.py verify-probe --config eval/agent-tasks/benchmark.example.toml --root "$ROOT" --agent codex --note "Describe the observed denied outside read and available context"
$PY eval/agent-tasks/benchmark.py run --config eval/agent-tasks/benchmark.example.toml --root "$ROOT"
$PY eval/agent-tasks/benchmark.py report --config eval/agent-tasks/benchmark.example.toml --root "$ROOT"
```

The example config is a matrix definition, not a recommended first full run: it expands to many paid sessions. Edit the task, agent and library lists before running. If `command -v codex` prints nothing in your Terminal, set `CODEX_BIN` to the CLI's absolute executable path; an empty expansion is rejected before a session starts. `setup_env.py --only harness,hmplot,baselines,all,javascript` can install a subset. It installs Python conditions into separate venvs, including an `all` environment for unrestricted Python library choice, and JavaScript packages in the scratch `javascript` environment. Its scratch `package-lock.json` and `versions.json` record resolved dependency versions. `npm install` runs only in the scratch root, never this worktree. The old single-run [run.py](run.py) and hand-written Python [references](references) remain available for reference validation.

After setup, data preparation and the reviewed probe, `benchmark.py run` is a sequential queue. Repeat the same command to resume it. `workflow/manifest.json` freezes the expanded matrix, CLI identities, task prompts, guidance, harness source, dependency versions and pinned source hashes. A changed manifest requires a new root. A process lock prevents duplicate workers. Completed trials are skipped even when the chart failed or needs visual review; an unsuccessful chart remains a result. Authentication, isolation and interrupted CLI sessions pause the queue.
```sh
$PY eval/agent-tasks/benchmark.py run --config eval/agent-tasks/benchmark.codex.toml --root "$ROOT"
$PY eval/agent-tasks/benchmark.py status --config eval/agent-tasks/benchmark.codex.toml --root "$ROOT"
# After investigating an interrupted attempt, archive it and resume explicitly:
$PY eval/agent-tasks/benchmark.py run --config eval/agent-tasks/benchmark.codex.toml --root "$ROOT" --retry-interrupted
```

`--max-sessions N` limits one invocation, reserving both possible calls before starting a trial; it stops between trials. Retries preserve old run directories, traces and accounting in `workflow/archives/`. Raw output streams directly to JSONL/stderr files while the CLI runs. Timeouts stop the CLI process group and retain partial output; incomplete token usage is labeled, never presented as a known zero. Codex cached input is counted once, and the raw provider usage is retained. All attempts retain code, HTML/PDF files, logs, checks and screenshots. New corrections clear generated final outputs so a failed correction cannot display a stale plot beside its changed program.

## Agents and conditions

Claude Code, Codex CLI, and Gemini CLI use separate adapters. Every configured agent needs a working login **and** an isolation probe. The probe tries to read a sentinel outside its run directory and asks about project files, memory, plugins, MCP and web access. The harness reads the raw JSONL trace and rejects a visible sentinel even if the agent omits it from its final answer. An operator must also inspect the trace for leaked project instructions, personal memory, plugins, MCP and web tools before running `verify-probe --note`. This binds verification to the trace hash, executable path/version/hash, model and adapter policy; a changed binary or policy requires a new probe. Generic bundled system skills are recorded and shared across conditions; personal/project skills and instructions must be absent. Authentication or permission errors keep it unverified. Do not bypass a refusal. Every run records CLI version, requested model, tool policy, raw output, parsed tokens, wall time and correction attempts. Codex requests a custom permission profile with outside reads denied, the selected Python environment read-only, and network disabled; it also disables host skills, plugins, apps, memory and multi-agent features. Before a paid Codex probe, a **no-model sandbox preflight** checks inside reads/writes, denied outside reads/writes, symlink escapes and path aliases. Each trial repeats the check with its selected Python environment readable but not writable. A failed preflight blocks all task sessions, even if its JSON is manually marked verified. Codex corrections receive the full original instructions again, start in the same run directory and edit the previous solution; Claude and Gemini use their resume options. The adapter parsers have a captured Claude login-failure fixture, a normalized captured Codex permission-failure fixture, and representative successful JSON/JSONL schema fixtures. Live Claude and Gemini sessions remain unverified here.

`hmplot` gives the dedicated Python condition local docs and `hmplot-skill/SKILL.md` with a direct instruction to read both. `hmplot-cold` gets neither. `free` (and its older alias `free-baselines`) offers only baseline Python packages, or none; `free-all` also installs HMPlot and exposes its docs as optional material without instructing the agent to use it. The JavaScript track offers `hmplot-js`, `free-js`, `deckgl`, `observable-plot`, `free-js-baselines`, and `free-js-all` under the same distinction; `hmplot-js` gets the docs and skill too. Its five seeded tasks are scatter, linked brushing, million-point filtering, map points and 3D points; three real-data tasks also support JavaScript. A Svelte component may import CSV text with `?raw` or binary data with `?url`, then use HMPlot, deck.gl or Observable Plot. The harness bundles it into one offline HTML file and runs the same browser checks. Library actually used is inferred from imports and must be confirmed in visual review for free-choice runs.

Generated Python programs and JavaScript bundles are evaluated under a per-run macOS `sandbox-exec` profile that limits reads, writes and network access; the Python runner also uses a blank home. Non-macOS hosts need equivalent isolation before running untrusted programs. Chrome checks use DPR 2 and block network. PDF checks use poppler when present, else PyMuPDF. Hidden WebGL/WebGPU row counts remain `unknown` and require review; requestAnimationFrame cadence is recorded only as a diagnostic, not as completed chart frame rate.

### Svelte web-authoring comparison (2026-10-21)

`complex.web.toml` defines fifteen hard tasks × two models (`gpt-6-luna`,
`gpt-6.1-sol`) × three conditions, one repetition and up to two corrections:
**90 trials**, excluding probes, smoke tests and references. The seeded order rotates
conditions within shuffled task/model blocks. Results are exploratory, not a
multi-repetition estimate. No separate paid model-judge pass is configured.

Both HMPlot conditions install the same npm tarball, types and `hmplot/check` entry
point. `setup_env.py --hmplot-package <tarball>` records package and dependency-lock
hashes and removes bundled guidance from the installed package. The old guidance is
frozen under `artifacts/web-authoring/baseline` with a 505-file SHA256 manifest; the new
condition uses the reproducibly generated `build-llm/standard` bundle and Svelte skill.
Never regenerate or overwrite the baseline. A deterministic copy is retained in
`baselines/web-authoring-old-docs.tar.gz`, with its file manifest beside it. Restore
it into an empty `artifacts/web-authoring/baseline` directory with `tar -xzf` and
verify every file against the manifest before a new evaluation. Keep evaluation
roots outside the checkout.
Reference sources, screenshots and galleries must not be readable by evaluated agents.

Native Svelte submissions compile with `svelte-check`, then build from package exports
without checkout aliases. The harness explicitly installs its inspection hook and
returns structured diagnostics and screenshots after each attempt. Offline builds inline
HMPlot workers using the same strategy as the standalone exporter. A screenshot change
alone leaves interaction correctness unknown. Device loss is an infrastructure failure;
it stops that trial without consuming a task correction. Preserve its artifacts before a
bounded, explicitly recorded retry.

The fifteen `references/<task>/hmplot.svelte` programs preserve the Python references.
Run `run-web-references.py <root> --tasks <comma-separated IDs>` against an installed
package environment. `--reference-only` skips duplicate generic gestures and runs the
independent data/geometry/DOM oracles; `--build-only` only compiles. Each full reference
run saves `reference-checks.json`, `reference-initial.png` and
`reference-interaction.png` at DPR 2. These solutions are excluded from both guidance
bundles. Review the saved images as well as the deterministic assertions and record
reviewer provenance and unresolved requirements.

`benchmark-web-references.py <root> --out <directory>` measures all fifteen production
pages in five fresh browser contexts each, then six representative interactions in three
warmed five-second samples. It records startup, input-to-corresponding-draw latency,
completed-frame rate and observed frame intervals, hardware/browser versions and artifact
hashes. Run serially without other GPU tests. A fresh page does not clear the shared Metal
shader cache; the report explicitly distinguishes startup from unmeasured genuinely cold
shader compilation. Publish the raw measurements and methodology with the results.

Visual reviews can record `--review-source coordinating-agent --reviewer "<identity>"`
when performed by the implementation agent; do not label them as human reviews.
Post-interaction native inspection reports are preserved per attempt in
`hmplot-check-after.json`, alongside the initial report and screenshots.

Before the queue starts, the harness copies each selected guidance bundle into
`frozen/guidance`, makes its files read-only, and records their hashes. Resuming
refuses changed source or snapshot bytes. Node, npm and Chrome executable hashes
are recorded and checked alongside package and dependency-lock hashes.
`--first-attempt-review` and `--first-attempt-note` record an independent review of
the retained round-0 artifacts; `first_attempt_correct` is null when unresolved.
This differs from the historical `first_try` field, which means a final pass with
no correction. Final reviews also accept `unknown`, preserving reviewer provenance
without promoting unverified requirements to passes.
